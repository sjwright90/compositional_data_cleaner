# T11a: Shared plumbing (gates in collections, blocking severity, vocabulary usage)

**Spec:** §4.1, §8 (08-config-audit); A3, A7
**Depends on:** T10
**Status:** done (part of the T11 split; see `tasks/T11.md`)

**Goal:** Give stages five missing facilities before the first real stage exists: gates discovered inside lists and dicts of sub-models, data-dependent gate defaults (`Stage.suggest`), data-dependent param entries (`Stage.sync_params`), a blocking severity that stops commit and the runner, and vocabulary-usage reporting so the recipe `config` snapshot holds only referenced entries. No stage is registered; everything is tested with stub stages.

## Implement
1. **Gates inside collections.**
   - Keep the class-level `gate_fields(params_cls)` signature. Add an instance-based `gate_paths(params)` that also walks `list`/`tuple`/`dict` fields whose elements are sub-models, producing indexed paths such as `sheets[2].layout` or `maps[mn].unit` (dict key in brackets).
   - `unresolved_gates`, `accept_defaults`/`_accept`, `gate_default_drift` and the gate-row logging in `Project.commit` use `gate_paths` and a path resolver that understands `[i]`/`[key]`.
   - Gate paths for list elements use `[i]`, for dict entries `[key]`. Dict entries are the preferred form for keyed decisions (T11c uses `dict[str, SheetContract]`); list support stays generic. A stage that uses a list must match decisions by stable key, not position (invariant 3), and its task says so.
2. **Data-dependent gate defaults.**
   - Optional pure method `Stage.suggest(inputs, params, vocab) -> Mapping[gate_path, value]`, declared on the protocol as optional. A gate declared with `gate_field(default, suggested=True)` takes its default from `suggest` instead of the static value.
   - `preview` is unchanged (unresolved gates raise `UnresolvedGatesError`). `Project.suggestions(name) -> SuggestResult(values, report)` syncs, calls `suggest`, never writes and works while gates are unresolved (one `gate_suggestion` item per unresolved suggested path); it raises `UnresolvedGatesError` only for a stage without `suggest` whose upstream is not runnable. The runner lists suggestions next to unresolved gates.
   - `accept_defaults` takes the suggestions and stores the RESOLVED value (`{"accept_default": true, "value": <resolved>}`), stage by stage in topological order. A `suggested=True` gate is resolved only from a suggestion: without one (no inputs yet, or `suggest` omits the path) it stays unresolved and is not accepted; `spec.default` is used for non-suggested gates only. `run_stage` and `commit` still require every gate resolved.
   - A3 drift detection for suggested gates compares the stored value with the current suggestion; `Project` computes it when the stage's inputs are available and reports it as a notice (logged at commit), not at recipe load.
   - Architecture tests: for every registered stage with `suggest`, it is deterministic (two calls equal) and does not mutate its inputs.
3. **Data-dependent param entries (`sync_params`).**
   - Optional pure method `Stage.sync_params(inputs, params, vocab) -> SyncResult(params, orphans)` (`orphans` are gate-path prefixes such as `entries[old]`), declared as an optional protocol. It adds entries for new keys, each with an unresolved gate; it never changes an existing entry. `sync_params` decides which entries exist; `suggest` decides their suggested values.
   - Orphans (entries whose key is no longer present): decided ones are kept in the recipe (§3.7), listed in `SyncResult.orphans`, excluded by `Project` from `unresolved_gates`, `accept_defaults`, drift and commit gate rows, reported as one `orphan_decisions` info `ReportItem` (count, keys) and ignored by the stage's run; undecided ones are dropped by `sync_params` (the only removal case). If the key reappears the kept decision applies again.
   - `Project` applies `sync_params` in topological order wherever it needs a stage's current params: `preview`, `run_stage`, `commit` and the unresolved-gates listing. The synced params are held in `Project` (so they are written to the recipe). A dependent's new entries appear only once its upstream has run; until then the stage is BLOCKED as today.
   - Architecture tests for every registered stage with `sync_params`: deterministic, does not mutate inputs or params, and idempotent (applying it twice equals applying it once).
4. **Blocking severity.** `ReportItem` has no severity field today (only `warning: str | None`), so add `blocking: bool = False`; a blocking item must carry a `warning` text (checked in `__post_init__`). The cache round trip stores it (old cache entries without the key read as `False`).
   - `Project.run_stage`/`preview` return blocking items unchanged.
   - `Project.commit` raises a `ProjectError` subclass listing the blocking items before writing anything.
   - The runner prints each blocking item and exits 1; exit 2 stays for unresolved gates; `--help` documents it.
5. **Vocabulary-usage reporting.**
   - `Stage.run` keeps its signature. `Project` passes a `Vocabulary` view bound to a `UsageTracker` (e.g. `vocab.tracking(tracker)`), so lookups with `used=None` record into it.
   - The tracker's JSON is stored with the stage's cache entry (a cache hit still reports it; an entry without it is a miss with a warning item) and in the checkpoint manifest (`vocabulary_usage`). `Project.current_recipe()` embeds `Vocabulary.snapshot(used)` for the union over the head checkpoints' manifests only, never from the cache or in-memory runs (preview and uncommitted runs do not change the recipe hash; deleting `cache/` changes nothing).
   - Log the choice in decisions.md as the replacement for "file hashes only".

## Done when
- A stub `Params` with a list of gated sub-models reports unresolved paths `<stage>.sheets[0].layout`, … sorted; `accept_defaults` fills each; drift warnings name the indexed path; `commit` writes one gate log row per indexed path with the right `user` / `default-accepted` type.
- A stub stage with `suggest` and a suggested gate: `Project.suggestions` returns the values and `gate_suggestion` items while gates are unresolved and writes nothing; `preview`, `run_stage` and `commit` still raise `UnresolvedGatesError`; `accept_defaults` stores the resolved suggested value (not a sentinel); a suggested gate with no suggestion is not accepted and stays pending; changing the upstream data changes the suggestion and produces a drift notice naming the gate; the arch tests fail on a planted non-deterministic or mutating `suggest`.
- Stub stage with `sync_params`: a new key adds an entry with an unresolved gate listed at its path (`<stage>.entries[<key>].decision`); an existing decision survives a sync unchanged; a decided orphan is kept, excluded from gates, reported by one info item and ignored by `run`; an undecided orphan is dropped; a reappearing key reuses its old decision; applying `sync_params` twice equals once; a dependent stage's new entries appear only once its upstream is runnable, and until it is committed it is BLOCKED; the arch tests fail on a planted non-idempotent or mutating `sync_params`.
- Existing flat-gate tests pass unchanged (same paths, same messages).
- A stage returning a blocking item: `run_stage` returns it, `commit` raises and writes no checkpoint, log row or head; the runner exits 1 and prints the item text; unresolved gates still exit 2.
- `ReportItem(blocking=True)` without a warning raises; a cached blocking item reloads as blocking.
- The recipe `config` snapshot contains exactly the vocabulary entries a committed stub stage looked up; it is identical after a cache hit, after a fresh `Project` with `cache/` deleted, and unchanged by `preview`.
- Fingerprints of existing stub stages are unchanged (golden fingerprint test passes).
- `./scripts/check.ps1` passes.

## Out of scope
Any real stage, header parsing, config/fixture changes (T11b), UI display of blocking items or suggestions.
